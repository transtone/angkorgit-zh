# 04 项目切换数据加载更新方案

状态：已完成代码实现与自动化验证接入，真实 Windows Tauri 仓库性能待实测。本文件同时保留设计依据，作为合并上游后的恢复契约。整体入口见 [README](README.md)，视觉细节见 [02 页面样式](02-page-styles.md)。

## 目标与边界

更简单的做法：复用现有 Zustand store 和刷新命令，为已经访问且仍打开的仓库标签保存内存快照。切回时先恢复该仓库旧数据，再后台刷新，查询完成后原位更新。

本次需要达到：

- A→B→A 切换到有缓存的项目时，第一幅可用画面就是目标项目旧数据，不等待 Git 查询。
- 不清空表格后重新加载，不以全工作区遮罩掩盖数据切换。
- 必须等待的加载只在提交表格区域使用透明遮罩；已有缓存的普通后台刷新仅显示轻量刷新指示。
- 数据、筛选、选择及阅读位置按仓库隔离；快速切换不串仓、不被旧响应覆盖。
- 刷新失败保留内容和标签，允许重试；首次打开失败另行处理。

不包含：跨重启磁盘缓存、离线数据库、每个标签常驻 React 页面、全部仓库持续文件监听、自动预加载所有最近仓库、WebSocket 推送、通用缓存框架。这里的“实时更新”指查询完成后直接更新当前表格，不承诺持续订阅所有非活动项目。

## 实施前的源码流程与问题

1. `RepoTabs` 调用 `activateTab(path)`，后者与首次打开一样调用 `useRepo.open(path)`。
2. `open` 设置 `opening`，等待 `ipc.openRepository`；换仓库时清空状态、分支、标签等数组，设置 `refreshing` 并等待 `refresh()`。
3. `refresh()` 并行查询仓库信息、状态、分支、标签、暂存栈、远端、子模块、冲突、工作树和未推送提交。多数结果统一写入，慢查询会拖延整体完成。
4. `RepositoryPage` 以 `opening || refreshing` 驱动整个三栏工作区遮罩，250ms 后出现，至少显示 450ms；背景为 `bg-background/95` 且带模糊。
5. 仓库路径改变后，页面清除提交选择及 Diff/编辑器/文件历史，调用图 store 的 `reload`。
6. `useGraph.reload` 在换路径时清空提交及布局，重新查询首批 200 条；`CommitGraph key={repo.path}` 重新挂载，浏览位置没有按标签恢复。
7. `activateTab` 把打开过程中的异常统一视为打开失败，并关闭标签。后台刷新引入后不能沿用这个错误分类。
8. 文件监听只跟随活动仓库。自动 fetch 由页面另一个 effect 驱动，不属于本地数据缓存；其完成后仍需按既有监听/刷新路径让界面收敛。

这些是静态源码结论，未测量实际 Git 查询耗时，不能据此断言某一个查询是主要性能瓶颈。

## 用户可见状态

| 状态 | 内容 | 加载反馈 | 失败处理 |
| --- | --- | --- | --- |
| 首次打开，无快照 | 切到目标仓库上下文，显示空表格容器 | 仅表格内容区透明加载；不显示前一仓库的行 | 局部错误和重试；路径不存在按原规则处理 |
| 激活，有快照 | 立即恢复目标项目表格、侧栏和状态 | 表头小型刷新指示，不拦截阅读 | 继续显示快照，轻提示及重试，不关标签 |
| 手动刷新 | 保留现有内容 | 仅表格透明遮罩；阻止表格内需等待的重复操作 | 去掉遮罩，保留内容，给出失败原因 |
| 文件监视触发刷新 | 保留现有内容 | 轻量后台状态，避免频繁遮罩 | 不清空数据；允许重试 |
| 刷新成功且无变化 | 保留内容、位置、选择 | 立即结束刷新反馈 | 不适用 |
| 刷新成功且有变化 | 原位更新对应数据 | 立即结束刷新反馈 | 被删除/改写的选中提交按明确规则退回 |

首次路径发现/校验阶段可以保留原项目，但必须明确当前仍是原项目，不能先将标签和标题切成 B 却展示 A 的数据。对于已有快照，路径已规范化，可立即恢复 B；异步确认目录失效后显示 B 的失效状态，不自动执行其他项目的操作。

## 缓存内容与生命周期

以 Rust 返回的规范仓库路径为键；工作树使用自己的工作目录路径，不能与主仓库合并成一份状态。Windows 大小写/斜杠差异优先复用现有路径规范，不能另造与最近仓库不一致的键。

| 内容 | 保存规则 |
| --- | --- |
| 仓库数据 | `repo`、`status`、`branches`、`tags`、`stashes`、`remotes`、`submodules`、`worktrees`、`conflicts`、`unpushed`、`pullPreview` |
| 仓库相关元数据 | `profileId`、`lastFetchAt`、`fetchFailures`，避免每次切回被重置；`statusVersion` 仍作为刷新信号正确递增 |
| 提交图 | 已加载 commits、rows、maxLane、hasMore、当前分支筛选、布局状态 |
| 阅读状态 | 选中提交 OID、多选集合、查找条件、纵向锚点及偏移、横向滚动位置 |
| 不缓存 | store action、DOM/虚拟列表实例、Timer、监听句柄、Promise、过渡 loading/error、全局最近列表 |
| 长操作状态 | 保留原有按仓库维护的 hook/提交草稿/终端会话机制；不能缓存并盲目恢复全局 `busy` |

- 切离前保存当前快照；失效的后台响应直接丢弃，非活动仓库再次激活时重新查询。
- 关闭标签释放快照和视图状态；标签关闭后旧响应不得重新创建快照。
- 应用退出自然释放；持久化标签列表不等于已有数据缓存，重启后首次访问仍是冷加载。
- 第一版仅保留已访问且未关闭标签，不加载全部历史。记录多标签、已加载多页时的内存占用；只有实测需要时才增加淘汰策略。
- `GraphLayout` 可变，不能让两个仓库共享同一个实例。保存独立布局或从缓存 commits 重建；实现时选择不会破坏增量分页且开销较小的一种，并测量大列表切换。
- 写操作成功要更新或失效所属项目缓存；上游新增数据字段时同步检查快照字段，不将旧数据结构直接持久化。

## 激活、刷新与请求隔离

### 激活事务

1. 记录离开项目的数据和阅读状态。
2. 为本次激活分配代次，读取目标快照。
3. 有快照时，在首次绘制前协调恢复 repo 与 graph 两个 store，并设置正确上下文；清理不属于目标仓库的临时 UI。
4. 再启动目标项目验证、本地数据刷新和 history 刷新。没有快照时走首次打开分支。
5. 刷新状态区分“首载、后台刷新、前台刷新”，不要继续用一个布尔值决定所有遮罩。

跨 store 的恢复必须作为同一可见切换处理，不能只在 `useEffect` 中滞后恢复 graph。React 18 的批处理也要通过逐帧测试验证，避免新 `repo.path` 搭配旧 rows 的一帧。可利用同步激活入口和适当的首绘协调，不为此引入新的状态管理框架。

### 请求规则

- 每个响应核对仓库路径、请求代次和标签存活状态；路径相同不足以处理 A→B→A 旧请求晚到。
- 保留并适配现有 `openSeq/fullSeq/statusSeq/previewSeq/requestSeq` 的防过期语义。全量刷新不能覆盖更晚的轻量 status 结果。
- 新刷新覆盖同仓库较旧刷新；可合并重复触发，但不允许请求乱序使状态倒退。
- 关闭项目和返回欢迎页同样使在途激活失效，防止关闭后打开请求重新写回仓库。
- Rust IPC 不支持取消的操作，不假装已取消后端任务；忽略失效响应即可，监听和前端计时器仍需清理。
- 快照恢复后保持本地状态刷新与历史刷新并行；先到的有效结果可显示，不能为等无关信息阻塞表格首绘。
- 第一版保留现有全量元数据查询结构，不拆成十套独立缓存。若实测仍慢，再按证据拆分关键状态和次要元数据。

### 监视器与自动获取

沿用活动仓库一个 watcher 的方案，保留 Rust watcher 的路径和代次保护。切换时停止旧 watcher、建立新 watcher，失败明确处理；恢复缓存不代替最新状态查询。非活动项目的外部更改在再次激活时收敛。

自动 fetch 保留设置、节流和失败提示，`lastFetchAt` 按项目恢复，避免切回就丢掉节流信息。fetch 不能成为显示缓存的前置条件；不把“快照命中”当作“远端已获取”。

## 表格更新与阅读位置

1. 恢复筛选后再查询对应历史，缓存与查询参数必须一致，不能先展示所有分支再跳回筛选分支。
2. 记录首个可见提交 OID 及行内偏移。新增提交导致索引移动时，按 OID 找回锚点；找不到时使用受限的原位置或表头作为明确回退。
3. 仍存在的选择继续保留；被 rebase/reset 改写或删除的选择清理，同时让右侧详情回到有效状态，不继续显示失效 OID。
4. 保留已加载页的阅读范围。刷新仍查询覆盖当前已加载范围的数据，避免返回首 200 条让深处阅读位置消失。
5. 不直接删除 `key={repo.path}` 以复用组件，因为组件内部搜索草稿、菜单和异步状态也需隔离。保留重挂载并显式恢复视图，或提供等价的完整重置/恢复，优先较小且安全的实现。
6. 查找条件可恢复，旧匹配索引不能盲目复用；历史变化后重新计算，并保留用户在请求期间的新选择。
7. 无变化时避免无意义地重建所有 rows/layout；比较相关数据而非只看 HEAD，因为 refs、stash 等也可能变化。
8. 第一版不缓存 Diff 正文或编辑器实例，沿用切换关闭这些临时视图的行为；恢复提交选择与滚动位置是本次范围。已有草稿保护不可削弱。

## 操作与错误边界

- 缓存可浏览不代表数据已验证。写操作继续使用原有后端验证，必要时先刷新与该操作有关的状态，而非全局锁住页面。
- 快进、重置、丢弃、提交等在发起时绑定仓库路径、分支/OID；完成回调只更新所属仓库，不能借当前 store 路径写入另一个仓库。
- 分支菜单中的可执行判断后台重验，未确认时不沿用过期的“可以快进”。
- 首次路径发现失败与缓存刷新失败分别处理。已有缓存的网络/查询失败不能由 `activateTab` 的 catch 关闭标签。
- 文件夹确实不存在可以沿用已有失效标签处理，但不能把暂时的权限或查询错误当作目录消失。
- 刷新失败要清理对应 loading；重试只作用于该项目。图刷新成功、元数据失败等部分结果要明确呈现，不回滚到更旧快照。

## 测试与验收矩阵

实施时先增加能重现当前清空/遮罩行为的测试，再实现。建议 store 单测使用 deferred Promise 控制响应顺序，e2e 使用已有 demo/IPC 测试入口；不靠随机 sleep 构造竞态。

| 场景 | 必须验证的结果 |
| --- | --- |
| 首次打开，查询延迟 | 仅表格局部加载；无其他项目行；其余面板不被遮罩 |
| A→B→A，A 刷新挂起 | 未释放新响应前已显示 A 的旧行、分支和文件状态 |
| A→B→A，多批响应乱序 | 最早的 A 响应不能覆盖最后一次 A；B 不串入 A |
| 元数据快、history 慢及反向组合 | 不出现新仓库标题配旧仓库表格；反馈能正确结束 |
| 缓存后台刷新失败 | 标签及旧内容保留，错误可重试，loading 清理 |
| 关闭正在加载的标签/关闭全部 | 旧结果不能复活标签、缓存或覆盖新项目 |
| 外部提交或 ref/stash 变化 | 切回先有旧数据，后台结果正确收敛 |
| 新提交插入顶部 | 阅读锚点、仍有效的选择和详情保持稳定 |
| 分支筛选、搜索、多页阅读 | 切回恢复筛选和位置，刷新不缩回首 200 条 |
| 旧选中提交被改写 | 明确退回有效状态，无失效详情或错误写操作 |
| 手动刷新、键盘操作 | 局部遮罩不覆盖外区；不能通过键盘绕过表格操作约束 |
| 明暗主题、窄窗口、Diff/编辑器 | 无白屏/模糊，无遮罩越界，不覆盖其他中心视图 |
| 非活动项目操作完成 | 只更新该项目状态，不污染当前仓库；原草稿不丢失 |
| 反复开关多个项目 | watcher/计时器无累积，关闭后快照释放 |

性能验证分开记录：点击到缓存首绘、点击到新数据、Git 查询耗时、已加载多页和多标签的内存。使用至少两个真实仓库在 Windows Tauri 中检查，包括截图中带较多未提交文件的场景。目标是缓存首绘不依赖 IPC 完成，不预先承诺未经测量的毫秒指标。

自动测试按总入口运行 typecheck、单测和 e2e；未改 Rust 时不因本方案重复构建整个 Rust 引擎。桌面实测记录仓库规模、标签数、是否自动 fetch、测试版本和结果。
