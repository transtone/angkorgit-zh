## 文件维护规则

1. 本目录记录“为什么、必须保留的行为、定位入口、恢复步骤和验证方法”，源码仍是实现事实来源。
2. 上游移动文件或改名时，按符号与行为查找新入口，更新专项清单；行号不作为恢复依据。
3. 文档中的“建议”“待实施”和“计划测试”不能记为已完成。实现合入后补充实际提交、测试结果及限制。
4. 上游已有等价实现时优先复用，只补缺失行为，不重复维护第二套功能。
5. 不将 `git checkout` 整体恢复源码文件、整提交重放或 `-X ours/theirs` 当成定制恢复方案。一个历史提交可能同时包含翻译、样式、功能和生成文件。
6. 当前工作区已有的 `features/updater/check.ts` 修改及 `tests/unit/updater.test.ts` 不属于本方案，不覆盖、不归入本次实现。

## 每次合并上游的流程

### 合并前

- 按 [上游同步说明](../upstream-sync.md) 确认入口。当前 `package.json` 未声明 `upstream:sync`，不要直接假设该快捷命令存在；核对脚本及 Actions 后选用已有入口。
- 提交或自行暂存现有工作，记录合并前提交和上游目标提交，保留合并祖先关系。
- 阅读四份专项文件，比较上游在清单路径及其新替代模块中的改动。

### 合并后

1. 逐项确认保留的行为；没有 Git 冲突也必须检查，自动合并成功不等于定制还在。
2. 先适配功能和结构：严格快进、项目切换与请求隔离；再恢复样式和新增中文文案。
3. 使用已有词典流程处理翻译，人工处理模板表达式、多行错误及行为相关文案。同步更新测试选择器。
4. 分别执行专项验证，最后运行公共前端门禁；涉及 Rust 才增加相应 Rust 检查。
5. 在下面的记录表中登记本次结果；代码、词典、测试和维护文档一起交付。

公共检查命令（在仓库根目录，环境已安装依赖时）：

```bash
rtk bun run check:dict
rtk bun run check:copy
rtk bun run typecheck
rtk bun run test
rtk bun run test:e2e
rtk git diff --check
```

前端演示模式只能验证界面交互及模拟响应，不能代替 Windows Tauri 中的真实本地 Git、监视器与性能验证。Rust 命令和专项测试见快进清单。

### 恢复失败时

不要以隐藏错误或跳过检查替代恢复。将失败归到对应专项，记录触发步骤、上游变更和未满足的行为；未实现的切换优化保持“待实施”，不要误标为回归修复完成。需要撤销某项本地新改动时只撤销该项 diff，保留上游有效修复。
